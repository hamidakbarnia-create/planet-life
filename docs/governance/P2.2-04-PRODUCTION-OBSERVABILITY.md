## 2. Problem statement

After P2.2-01–P2.2-03, the Ask / Conversation decision path can run on staging with bounded provider behaviour, but operators still cannot reliably answer, from production-safe telemetry alone:

1. Whether Ask/conversation requests are succeeding or failing at meaningful rates.
2. Which **failure class** is rising (timeout, provider, validation, internal), without reading user reports.
3. Whether frontend/BFF, API, and provider boundaries agree on the same request identity when a failure occurs.
4. Whether a given **deployment version** introduced an operational regression.
5. Whether fallback / degraded paths are activating unexpectedly.

P2.2-03 already normalizes provider outcomes into `meta.providerExecution` on the Ask result path. That metadata is necessary but **not sufficient** as production observability: it is request-local, not an operator-queryable signal stream, and must not be expanded into logging of prompts or responses.

---

## 3. Objective

Deliver the **minimum viable production observability layer** for the Ask / Conversation decision path such that an operator can query, for a bounded time window and deployment identity:

- request volume and success vs failure rates;
- latency distribution (at least p50/p95 or equivalent buckets);
- classified failure counts by stable taxonomy;
- fallback/degraded activation rate;
- correlation via existing request identifiers;

**without** recording sensitive user content, **without** selecting a monitoring vendor in this specification, and **without** changing Ask semantics, localization, or API contracts.

Success is demonstrated by evidence that required signals are emitted, redacted, correlatable, and queryable — not by decorative dashboards or vendor adoption alone.

---

## 4. Required operational signals

Only signals justified by the current Ask/conversation architecture and residual production risk are required.

| Signal ID | What is measured | Origin (logical) | Required dimensions / labels | Forbidden high-cardinality labels | Verification |
| --------- | ---------------- | ---------------- | ---------------------------- | --------------------------------- | ------------ |
| **S01 Request volume** | Count of Ask decision orchestrations that reach the provider-execution boundary (or explicitly skip provider for clarification-only paths, counted separately if emitted) | Ask orchestration (`runAskDecision` / equivalent BFF boundary) | `route` or `operation` (`ask_decision`), `env`, `app_version` | user id, question text, prompt hash of content | Unit/integration: counter increments once per request; staging smoke shows non-zero volume |
| **S02 Outcome** | Success vs failure of the Ask orchestration result (fallback may still be HTTP 200 — classify by product outcome) | Ask result assembly | `outcome` ∈ {`success`, `fallback`, `clarification`, `error`}, `env`, `app_version` | raw error strings, message bodies | Assert mapping for success / fallback / clarification / hard error fixtures |
| **S03 Latency** | End-to-end Ask orchestration duration; plus provider-boundary latency when provider was called | Orchestration timer; `providerExecution.latencyMs` / attempt latencies | latency buckets or histogram; `env`, `app_version` | per-user labels | Fixture asserts latency recorded ≥ 0; staging sample shows finite latency |
| **S04 Provider failure class** | Count of provider-boundary failures by P2.2-03 taxonomy | `providerExecution.failureReason` / attempt status | `provider_failure_reason` ∈ published set (§8), `attempt_purpose` ∈ {`initial`,`language_retry`,`safe_regeneration`}, `env` | provider raw message, HTTP body, stack | Matrix tests for timeout, network, http, empty, invalid_output, cancelled, budget_exhausted |
| **S05 Validation / grounding degradation** | Count when claim-validation or grounding status is `unavailable` or Ask attaches unavailable meta on provider failure | Ask meta `validation.status` / `grounding.status` | `component` ∈ {`grounding`,`validation`}, `status`, `env` | claim text, evidence payloads | Fixture: initial provider failure → unavailable grounding/validation counted once |
| **S06 Fallback / degraded activation** | Count when structured fallback is used or `providerExecution.fallbackUsed=true` | Ask `meta.fallback` / `providerExecution.fallbackUsed` | `env`, `app_version` | user content | Orchestration test + metric assertion |
| **S07 Provider call budget usage** | Distribution or counters of `providerExecution.callCount` (0–2) | Ask `meta.providerExecution` | `call_count` ∈ {0,1,2}, `env` | — | Assert never emits call_count > 2; AR language-retry path may show 2 |
| **S08 Deployment / version identity** | Which build is serving | Build-time `NEXT_PUBLIC_RELEASE_SHA` / API release identity if present | `app_version` or `release_sha` (short), `env` ∈ {`staging`,`production`,…} | full env dumps | Staging/production evidence shows version label matching deployed release |
| **S09 Correlation id** | Presence of request correlation id on emitted signals | ADR-0007 `request_id` / Ask `meta.requestId` (§9) | `request_id` **only in logs/traces at low volume**, **not** as a unbounded metric label cardinality source | using raw `request_id` as a Prometheus-style metric *label* on high-volume series | Logs/events include id when known; metrics use ids only in exemplars/debug events, not as hot labels |
| **S10 Dependency health** | Liveness of staging/production API health endpoint used by Ask | Existing API `GET /` (or documented health route) | `service` ∈ {`api`,`web`}, `env` | — | Smoke: health 200; documented in closure evidence |

**Not required in P2.2-04:** product analytics funnels, per-question embeddings, token-usage billing metrics, full distributed traces across unrelated modules, World/News/Pathfinder-specific metrics.

## 7. Privacy and security constraints

### 7.1 Forbidden in logs, metrics attributes, traces, and dashboards

MUST NOT record:

- raw user questions / clarification answers
- conversation message bodies
- full prompts or prompt fragments containing user or profile content
- model / provider response bodies
- personal profile / birth data
- secrets, API keys, authorization headers, cookies
- provider credentials
- stack traces containing request payloads
- unnecessary precise IP, device, or advertising identifiers

Vague “avoid PII” is insufficient: treat the above as a hard deny-list.

### 7.2 Permit allowlist (operational fields only)

| Field | Permitted? | Operational reason |
| ----- | ---------- | ------------------ |
| `request_id` / Ask `meta.requestId` | Yes (logs/events; not hot metric labels) | Correlate FE/API/provider outcomes |
| `route` / `operation` | Yes | Distinguish Ask vs other surfaces |
| HTTP status (transport) | Yes | Separate transport failures |
| Error / outcome category (§8) | Yes | Stable failure aggregation |
| Latency value or bucket | Yes | Regression detection |
| `locale` | Yes | Detect locale-specific failure spikes (e.g. AR retry) without content |
| Provider **identifier** (e.g. `openai`) | Yes | Dependency attribution — not raw vendor errors |
| Model **identifier** (e.g. `gpt-4o-mini`) | Yes, if already configured in env and non-secret | Dependency attribution |
| `app_version` / release SHA | Yes | Deployment regression isolation |
| `env` | Yes | Staging vs production separation |
| `attempt_purpose` | Yes | Budget / retry / regen diagnosis |
| `provider_failure_reason` (enum) | Yes | P2.2-03-aligned classification |
| `call_count` (0–2) | Yes | Budget enforcement visibility |
| `fallback` boolean | Yes | Degraded-path detection |

### 7.3 Redaction rule

If a field is not on the allowlist, it is **denied** by default. Debug overrides that expand the allowlist are forbidden in shared staging/production without a separate governance change.

## 8. Error taxonomy

Stable categories for metrics and structured logs. **MUST NOT** use arbitrary provider error text as a metric label.

| Code | Meaning | Typical mapping | Class |
| ---- | ------- | --------------- | ----- |
| `client_input_rejected` | Request rejected before provider (validation of client input / clarification required counted under `clarification` outcome when applicable) | 4xx-equivalent product rejection | User/client |
| `timeout` | Provider-boundary timeout (P2.2-03) | `providerExecution.failureReason=timeout` | Dependency |
| `provider_unavailable` | Network / connectivity failure to provider or API | `network_error` | Dependency |
| `provider_http_error` | Non-OK HTTP / contract HTTP failure | `http_error` (+ optional status **bucket**: 4xx/5xx, not free-text) | Dependency |
| `provider_auth_config` | Auth/config class when distinguishable from generic HTTP (optional refinement; else remain `provider_http_error`) | 401/403 when classified | Dependency |
| `provider_rate_limit` | Rate limit when distinguishable (optional refinement; else `provider_http_error`) | 429 when classified | Dependency |
| `provider_malformed_response` | Empty / whitespace / unusable structured output | `empty_response`, `invalid_output` | Dependency |
| `provider_exception` | Normalized SDK/provider throw | `provider_exception` / `unknown_failure` at provider boundary | Dependency |
| `cancelled` | Caller abort | `cancelled` | Client/ops |
| `budget_exhausted` | Provider call denied by Ask budget | `budget_exhausted` | Internal control |
| `validation_unavailable` | Claim validation unavailable | `meta.validation.status=unavailable` | Internal/degraded |
| `grounding_unavailable` | Grounding unavailable | `meta.grounding.status=unavailable` | Internal/degraded |
| `internal_orchestration_failure` | Unexpected Ask pipeline defect after boundary normalization | catch-all internal | Internal defect |
| `localization_presentation_failure` | Localization/WQ presentation hard-failure **if** separately observable without content | rare; only if implementation can detect without logging copy | Internal |
| `unknown_internal_error` | Unclassified internal | last resort | Internal defect |

**Distinctions required in operator views:**

- User/client 4xx-style conditions vs dependency/provider failures vs internal defects vs deliberate fallback/degraded execution (`outcome=fallback` / S06).

## 9. Correlation contract

### 9.1 Identifier authority

- **Conversation HTTP (ADR-0007):** `request_id` on successful conversation envelopes remains authoritative for provider/API conversation calls.
- **Decision HTTP (ADR-0006):** `request_id` / `result.requestId` semantics remain as locked; P2.2-04 MUST NOT redefine them.
- **Ask client meta:** `meta.requestId` continues to carry the conversation `request_id` when a provider call succeeds; on provider failure, id may be null — signals MUST tolerate null ids.

### 9.2 Propagation

- Do not invent a second competing public correlation header without an ADR amendment.
- If an incoming client correlation header is later introduced, it requires ADR review; until then, server/provider-issued `request_id` is sufficient.
- When `request_id` is absent or invalid, generate or omit per existing client behaviour; do **not** invent user-visible contract fields.

### 9.3 Visibility

- `request_id` may appear in API responses as today.
- Observability may attach `request_id` to structured logs/events.
- `request_id` MUST NOT be used as a high-cardinality metric label on volume/latency series (S09).

### 9.4 Privacy

Correlation ids are opaque operational tokens. They MUST NOT embed user question text or profile data.

## 10. Dashboard / operational view requirement

No vendor is preselected. The implementation MUST provide an operator view (platform-native console, log query, or metrics UI) that can answer:

1. Is the Ask/conversation path currently receiving traffic? (S01)
2. What proportion of requests are failing or falling back? (S02, S06)
3. Which failure class is increasing? (S04, §8)
4. Has latency degraded vs recent baseline? (S03)
5. Are failures primarily provider/dependency vs internal? (§8 class)
6. Which deployment version is affected? (S08)
7. Are fallback paths activating unexpectedly? (S06)
8. Are provider call counts respecting the budget ≤ 2? (S07)

Decorative charts and arbitrary widget counts are not required.

## 11. Alerting boundary

**Decision:** Alerting is **limited to a minimal critical condition set**, and numerical thresholds are **not invented in this ratification**.

P2.2-04 implementation MUST:

1. Emit the signals required to support alerting later.
2. Document proposed alert conditions **semantically**, for example:
   - sustained zero traffic after expected load;
   - sustained spike in provider failure rate;
   - sustained spike in fallback rate;
   - sustained latency degradation;
   - health check failure.
3. Collect a short staging/production **baseline** window and record recommended thresholds in the P2.2-04 closure evidence **before** enabling paging alerts.

P2.2-04 MAY ship with non-paging health visibility only. Aggressive multi-condition paging is **deferred** until thresholds are ratified in the closure report (still under P2.2-04) or explicitly deferred to a later ops task named in that report.

## 16. Rollout and rollback

1. **Staging before production** for any new telemetry sink or SDK.
2. Observability MUST **fail open**: telemetry export failures MUST NOT fail user Ask/conversation requests (AC14).
3. Provide a **disable mechanism** (env flag or equivalent) to stop export without redeploying product logic where practical.
4. No secret leakage in configs committed to git.
5. No material user-visible latency regression attributable to synchronous telemetry; prefer async/non-blocking export.
6. After deploy: run §14 staging smoke; record version identity (S08).
7. Rollback: revert deploy and/or disable export flag; confirm Ask path healthy via S10 + sample Ask.

## 18. Non-goals and architectural invariants

**Preserve:**

- ADR-0006 Decision API Contract
- ADR-0007 Conversation API Contract
- Shared conversation pipeline
- Prompt authority / structured question authority (P2.1b-02)
- Input Analysis, UnifiedDecisionContext, Intent Template Registry, Reasoning Planner
- Provider abstraction and P2.2-03 provider-execution boundary
- Localization, Semantic Preservation, Writing Quality
- `ASK_MAX_PROVIDER_CALLS = 2`

**Prohibit:**

- Duplicate question injection
- Provider leakage into product contracts
- Raw prompt or response logging
- New user-facing behaviour or semantic output changes
- Broad refactors disguised as instrumentation
- Blocking request execution because telemetry delivery failed
